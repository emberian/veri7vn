# Whole-project review and horizon

The product is an Isabelle-native specialist engineering environment: source
editing, interpretation, diagnosis/repair, composition, justified results,
improvement and deployment. The [architecture](../docs/ARCHITECTURE_PROPOSAL.md)
and [acceptance criteria](../docs/product/ACCEPTANCE.md) remain the destination.
Current priorities do not narrow that destination to arithmetic or a prover wrapper.

## What we are building

The Workshop and resident runtime share source/package identities, native
admission, generated authority, typed outcomes and durable lifecycle. Completion
means ordinary users can carry a source revision through useful behavior and
continue after restart. Separate logical meaning, executable refinement,
observational qualification and current publication permission.

## The working baseline

A [captured standalone macOS package](../tests/deployment/evidence/standalone-aae0d7dd.json)
passed outside-checkout source editing/reopen, exact native arithmetic, recovery
and bundled browser Workshop checks. It needs neither system Python nor compiler.
Historical resident consumers also exercised cancellation, selective/last-owner
Forget and restart. These qualify exact captures, not newer working source.
Source Save does not activate the edited specialist.

Launcher verification improved in a bounded
[comparison](../benchmarks/envelope/standalone-hash-repair-comparison.json): reopen
22.005s→8.027s while retaining full integrity checks. One uncontrolled comparison
is not a whole-system performance envelope. [VALIDATION.md](VALIDATION.md) records
component and runtime evidence with their limits.

## Current integration checkpoint

Workshop convergence joins four real journeys: author/repair/Build, ask/Search,
conversation/adoption, and governed acquisition/use. Shared native parent
compilation and actual runtime consumers are the immediate convergence checks.
The user's remaining-budget priority is Oracle7 routing/metaprogramming and
documentation. Finish concrete joins and useful behavior; defer broad new schema
migration while retaining its obligations.

Build requires historical source/diagnostics, actual candidate/admission and
terminal status in CLI/browser. Conversation needs intrinsic non-reentrant gates,
exact observations, source ownership and durable adoption/recall. Effects need
atomic nonassertional response ownership/retrieval and restart without invocation.
Search needs actual charged worker/proof/publication and historical source/result
reconstruction. D74 separates cancelled execution from retained verification;
no-result source support remains necessary. D76 narrowly separates executable
Search lineage from actual HOL dependencies; authored context policy/graph/output
recovery remains separate work.

## Untouched scope now made explicit

The ledger separately tracks finite probability/statistics, literal formats and
calendar, bounded transcendental models, versioned policy evaluation, governed
SQLite observation, warehouse workflow, MCP workflow, catalogue/toolchain
artifacts, ordered-pipeline synthesis, retained typed program libraries,
conservative type development and adaptive cross-capability search. Active drafts
and planned packages retain their full consumer obligations. These children do
not replace remaining parent requirements such as feedback, local Film, richer
native packages and performance lowering.

## How to keep broad progress coherent

Integrate existing shared consumers first. Fan out by semantic family using the
same source/admission/execution interfaces; own the final consumer rather than
another handoff. Reduce proof/session and generated-representation rebuild costs.
Measure realistic workloads as capabilities arrive. Preserve usable installed
checkpoints while committing reviewable source progress. Native builds remain
serialized through the steward.

All [PO-01–10 and TB-01–05](PROOF_OBLIGATIONS.md) remain globally open/unqualified.
Meaningful checked subcomponents do not disappear, but their scope cannot expand
beyond actual proof assumptions and implementation linkage.

## Horizon, external gaps and decisions

The six siblings are [compatibility/design pressure](../docs/review/sibling-gaps.md);
full sibling migration is a separate D18 decision. Missing original relation/name
snapshots and extraction provenance constrain data parity (D17), not implementation
of the reader platform. Fixtures/replacements must be identified as such.

D16 governs external registry/chain/publication scope; local explanation/artifacts
remain core. D19 licensing and redistribution closure is unresolved. Sepref/LLVM
benefit requires an actual compatibility experiment; names alone establish no
backend or performance claim. Platform qualification and recipient usability
remain engineering work.
