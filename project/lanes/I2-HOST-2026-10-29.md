# I2-HOST: a Rust appliance host, 29 October 2026

## What was built

`native/oracle-host`, one Rust binary. It serves the same loopback wire
contract Mini already speaks (`/health`, `/capabilities`, `/operations`,
`/invoke`, `/query`, the tenant routing header, browser and Host refusals,
immediate busy), and routes every question through one rule:

- group 0: the native learned reader over the admitted image, and every
  admitted extracted organ (resident in `KernelExecutor`, each with its
  specialist's own acceptance rule);
- group 1: the Python Engine, as contained child processes running
  `tools/parity/answerers/oracle7.py` unchanged.

The first group in which any route takes the question decides it with
`admission::arbitrate`: agreement answers, a difference refuses, any accepted
refusal refuses, a failed route refuses. The Engine is asked only when group 0
read nothing. Every reply lists every route's outcome in `provenance.host`.
The rule, configuration and limits are written down in
[native/docs/HOST.md](../../native/docs/HOST.md).

`/invoke` serves 21 operations in-process: the six runtime operations over the
admitted image (release-bound to the host binary's own digest) and fifteen pure
operations linked from the provider crates. No PyO3 extension is used.

## Deploy shape, for the provisioner recipe

1. `oracle-host` built with `--features reasoning,science,incremental,bio,statistics,logic`.
2. The data image and its SHA-256 (tonight `var/data-20261029/reader-image-v3.sqlite`, `8fcb1db9…842f4`).
3. A writable state directory: the session store (`native.state`) and the `/query` journal.
4. The release declaration: `oracle-host manifest --image-sha256 … --core-limits …` prints it and its identity; it binds the binary, so it is regenerated per build.
5. Organ binaries with SHA-256 and acceptance (from `tools/runtime_contract.py acceptance`), e.g. `var/acoustics/bin/acoustics`.
6. The clingo binary and SHA-256 if `logic` is served.
7. An Engine checkout with its stores, its git revision, a Python with SHA-256, and this repository's `tools/parity/answerers/oracle7.py` with SHA-256. The answerer's `--state` must lie under this repository's `var/`.

`native/oracle-host/tools/make_config.py` turns those into the operator JSON.
The Engine scored tonight is `upstream/` at git `c5d6a29d5bc5e2525078e5a53afa1abf659e4d69`
(`BUILD_REPORT.json` and `RELEASE_HASHES.json`: head `oracle_release_runtime_w540`,
merkle root `04daf3ae…2476f`), not the 10.1 tip `c473d289…`. Checkout and
revision have no default; moving to a 10.1 materialization changes those two
fields only.

## What it cannot do yet

No Mini signing, authentication, public gateway or effect executors. One
Engine is shared by all tenants (separated by session name only). Pure
operations run in the host process with cooperative cancellation, not in a
killable child. Conversations do not cross providers. Organ answers carry no
unit field, so organ numbers are compared as text. See HOST.md.

## Questions for the reviewer

1. **HTTP crate.** I used no HTTP crate. tiny_http 0.12 (cached here) spawns a
   thread per connection with no cap and has no socket timeout API
   (`src/util/task_pool.rs`), so it cannot keep the reference server's
   16-connection cap and 5-second absolute ingress deadline; hyper needs an
   async runtime. `src/http.rs` is about 300 lines of HTTP/1.0, one request per
   connection. Is that the right trade, or should the cap/deadline be dropped
   in favour of a crate?
2. **The Engine's 3 wrong on the reader set.** They are the Engine's own
   prose answers on questions nobody deeper reads. Options: accept (they are
   what Mini serves today), or add a guard that withholds Engine prose on
   questions shaped like knowledge-base queries. A guard is a new rule, so I
   did not invent one.
3. **Reader refusals end the turn.** On 8 targeted questions the reader
   returns `refused` (answer form) and the Engine is never asked. That follows
   the admission rule (an accepted refusal is not "no reading"), but it means
   the reader's form vetoes block the Engine. Should an answer-form refusal
   count as "no reading" instead?
4. **Engine isolation.** One Engine serves every tenant by session name. The
   Python tenant pool gives each tenant its own Engine. Is shared acceptable
   for Mini, or should the host port per-tenant workers?
5. **Exact wire shape of `/query`.** The reply keeps `{outcome, reply:{status,
   response, path, ...}}` but `reply.provenance` now always carries `host`, and
   Engine replies keep their own provenance fields beside it. Mini reads
   status/response/path; please confirm nothing else is read.
6. **Process hygiene.** A failed journey-test run (before the test learned to
   stop its host on panic) left a host and its fake Engine whose PID files
   were in a deleted temporary directory, and my launch wrapper recorded the
   wrong PIDs for the two final qualification hosts. I killed none of them.
   All six processes (58200, 58246, 76696, 76699, 76715, 76716) were gone at
   the end of the lane; I did not stop them and do not know what did. The
   test now stops its host on drop and writes a PID file.
7. `var/i2-host/` holds 2.0 GB of this lane's scratch (mostly a separate
   extension build in `target-ext/`); it can be removed when the receipts are
   no longer needed.
