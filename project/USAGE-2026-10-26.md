# Using Oracle7: experiment and improvement batch

Ember asked for many agents to use Oracle7 and discover how to make it more
useful and powerful. This batch starts with real tasks and retained answers.
Source inspection explains behavior; it does not replace trying the tool.

The passing appliance is `var/appliance-20261026/candidate`. It is immutable
input. Original `upstream/` is also read-only. Use `.venv/bin/python -B` and the
shared `tools/usage/run_batch.py` runner once ready. It starts a private adapter
and workspace, retains complete replies, and limits the batch to three engine
processes at a time. Twelve agents can work concurrently on task design,
analysis and implementation without twelve engines competing for resources.

## Lane contract

Each lane owns `tools/usage/<slug>/`, `tests/usage/<slug>/`, a report at
`project/lanes/U1-<slug>.md`, and scratch under `var/usage-20261026/<slug>/`.
The runner lane alone owns `tools/usage/run_batch.py`, its README and
`tests/usage/test_runner.py`. Root owns this record, integration and Git.
No lane spawns agents or edits another lane's files. Read repository AGENTS.

Start with 8–15 concrete questions/turns representing a plausible user's task.
Include ordinary wording, a boundary or ambiguity, and a follow-up where useful.
Write expected results independently before querying. Case files passed to the
runner contain only `id`, `conversation_id`, `text`; store expectations separately.
The runner accepts up to 30 cases, each within the adapter's 16 KiB request bound.
Use a new output directory for each run and retain unexpected answers.

Judge task completion, correctness, useful refusal, needless refusal, friction,
latency and whether the evidence actually supports the answer. Distinguish
engine defects, unavailable data, interface limitations and merely inconvenient
wording. A rewritten prompt is a workflow workaround, not a repaired engine.
Do not label a guessed answer or an LLM's analysis as Oracle output. Do not
transform withheld answers into successful ones or strip inconvenient evidence.

Implement one useful improvement in the owned area: a reusable workflow,
structured caller, evidence inspector, task pack, or a concrete regression and
repair. For changes to shared upstream modules or veri7vn families, identify the
exact files and ask root for ownership; while waiting, implement the repair in
an isolated small source copy under scratch and retain the patch. Never copy the
15 GB stores or hardlink writable source. Never modify the passing appliance.
No broad package downloads or builds. Isabelle builds require root coordination
and the designated lock/host tooling. Ordinary CPU-only narrow checks are fine.

Reports give exact task outcomes and examples, changed files, tests, limitations,
and the user who benefits. State explicitly when no specialist panels were run.
These usage experiments are not a replacement for the shipped six-criterion
panels or evidence of a fleet-wide score. No new theorem claim without its
statement and actual connection to the implementation.

## What actual use found

Twelve usage lanes completed their initial tasks. These are small, deliberately
challenging user-task samples, not random benchmarks or shipped specialist panel
scores. Their reports retain the original questions and unsuccessful replies.

The recurring problem is binding the question to the computation or source:
which number base, which person's full name, which relation, which physical
quantity, which sentence's conditions, and which conversation turn. Agreement
between two computations does not repair a shared mistaken interpretation.

Useful caller tools now include explicit-role finance and engineering inputs,
multi-step workflows with labelled local arithmetic, document/source mapping,
a capability search, evidence inspection, and a working transfer-time extension.
They preserve Oracle replies and identify their own calculations separately.
They do not turn natural-language failures into successful engine scores.

Root authorized scoped repairs in the private source checkout:

- composer versus notable-work relations;
- original digits and source base in both converter copies;
- finite numerical comparison in all three math-organ versions;
- conflicting supplied passages;
- contradictory geometry dimensions;
- delivered-reply conversation state and optional metadata;
- complete entity identity, creation versus development, and same-label entities;
- retained heating conditions across sentence boundaries;
- requested energy quantity and battery runtime roles.

The first combined candidate is `var/usage-20261026/candidate-first`. Actual
replay confirmed the composer, document-conflict, geometry and stale-conversation
repairs. It also exposed an explicit-null metadata regression and repairs hidden
behind a duplicate converter and later math-organ overrides. The failed runs
remain in the lane receipts; fixes must reach the actual imported consumer.

The original `var/appliance-20261026/candidate` remains the immutable baseline.
Each replacement is separately provisioned from the pinned source, recorded
patches, existing verified data cache, Earth overlay and adapter. Historical
upstream admission/release hashes are not rewritten to imply fresh qualification.

## SPK limits are separate decisions

The current Sandstorm SPK schema represents each regular/executable file as one
Cap'n Proto `Data` value. Its 29-bit byte count limits an individual file to
536,870,911 bytes, regardless of package compression. This is inherited format
structure, not an Oracle7 limit or a whole-package limit. Larger single files
need a compatible chunking/reassembly design or an explicit format extension.
Sources: [SPK schema](https://raw.githubusercontent.com/sandstorm-io/sandstorm/master/src/sandstorm/package.capnp)
and [Cap'n Proto encoding](https://capnproto.org/encoding.html).

Mini's separate 256 MiB raw-package admission cap is our own rule in
`Kernel/ApplicationSpkPackageIdentity.lean`. It can be revised along with its
consumers and validation. Importer CPU/memory/disk/time budgets are also ours;
the operator profile does not itself bypass admission. A runtime package with
shared immutable data is a useful deployment choice, not a requirement imposed
by Oracle7. Extending the format is another choice we control, with compatibility
and file-integrity work attached.

## Remaining work revealed by the batch

- Date storage has discarded precision: Shakespeare's stored first-of-month
  placeholder is printed as an exact birthday. Restore precision-bearing source
  data or expose the uncertainty; do not infer that every day-one date is coarse.
- Many valid requests still clarify or withhold, including summaries, prose
  finance questions, spring energy and quantity-bearing follow-ups. The new
  caller workflows make selected tasks usable but do not solve general routing.
- The Mars-year composition request still returns Earth's orbital period rather
  than converting three Mars years. Requested quantity coverage must reach the
  space route too; the energy repair does not solve that separate consumer.
- Older deictic substitution mistakes grammatical `it` for a conversation
  referent. The transfer specialist demonstrates useful completion outside that
  route; it is a local Workbench extension, not a newly proved kernel.
- Identity ambiguity, exhaustive lists and date qualifiers still need explicit
  handling. Missing precision/coverage cannot be manufactured by a reader.
- Repeat relevant deployed checks on Linux, where extracted kernels participate.
  This batch's local full-engine observations describe macOS Python routing.
