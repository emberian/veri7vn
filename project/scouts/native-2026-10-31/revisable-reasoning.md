# A knowledge workspace that can change its mind

Research/design scout, 31 October 2026. No implementation, builds, tests or commits; no specialist-panel numbers. Recommendation: retain identified evidence and revision-bound answer receipts in the host, while initially keeping both native providers stateless. Make retained solvers an optional cache after measuring real revision workloads.

## What exists

`native/oracle-logic/src/lib.rs::{Request,check_model,encode}` accepts one finite grounded normal program: indexed atoms, positive/default-negative bodies and integrity constraints. Its handwritten Gelfond–Lifschitz reduct checker checks returned models; it is neither an Isabelle theorem nor a certificate of exhausted search. `process.rs::query_program` first checks consistency, then seeks opposite-polarity witnesses for queries. `process.rs::solve` starts a fresh pinned clingo subprocess each time. Thus one hosted query can repeat process startup and the same grounded program across several probes. Returned witness checks establish existence or counterexample; skeptical truth, credulous falsity and inconsistency still trust solver UNSAT.

`src/hosted.rs::{program_identity,request_identity,call}` binds numeric program content separately from scope/labels/queries. `tools/oracle_components/logic.py` requires `complete_program=true`, explicitly a caller assertion. This means complete representation of the supplied policy, not complete knowledge of reality. No arbitrary ASP text, grounding, disjunction, optimization, classical negation or inter-call state is exposed.

`native/oracle-incremental/src/lib.rs::evaluate` maintains supported-edge reachability through finite versioned batches with differential dataflow. Fact IDs distinguish independent supports for the same edge. Retraction removes one support, with final set thresholding and recursive settlement. `rooted.rs::evaluate_rooted` restricts the maintained view to fixed upstream/downstream roots. Hosted rooted-v2 defaults to fresh recomputation; differential is host policy. Both drop all state after the call. The README records the earlier 48-node all-pairs experiment losing to BFS (74.234 versus 7.556 ms), not evidence of a general incremental speedup. Reachability is possible impact, not a proof that a conclusion lost its last derivation or became false.

`tools/usage/hosted_reasoning.py::BuildPlan` already contains the seed of the required consumer: identified evidence tokens, source labels, withdrawal history, atomic draft revision and full immutable program snapshots. Its fixture has dependency readiness, risk exceptions, alternative cache/rebuild plans and conflicting verification observations. This state lives in the demonstration client. `Client.invoke` explicitly repeats whole snapshots on retry; request IDs are correlation, not durable replay. Promoting this representation into a host-owned workspace is a smaller, more useful step than introducing a general reasoner.

## Three designs, with different jobs

**1. Durable evidence, fresh derived answers — recommended first.** A workspace is `(authenticated tenant, workspace_id)` with monotonically increasing committed revision. Store immutable assertion records: `fact_id`, typed atom/sign, source record and revision, observed time, valid interval, active status; retain withdrawal/supersession events. Rule bundles and coverage assertions have independent IDs and versions. A mutation transaction carries expected revision and idempotency token. It either commits all changes once or rejects stale revision; retries return the same committed result. Unknown retractions and ID reuse are errors. Durable commit and successful reasoning are separate outcomes: a timed-out solve cannot silently undo accepted evidence.

Produce a finite normalized snapshot for existing providers. Atom indexing is local to that snapshot; stable external atom IDs must survive remapping. Bind receipts to evidence revision, exact program digest, rule/compiler version, query and coverage revision. A solver cache key can omit provenance only for computation reuse; the presented receipt must still identify the new evidence revision even if its semantic program is unchanged. Host owns persistence, tenant isolation, admission and crash replay; providers remain pure.

Record alternative justifications as a bounded AND/OR graph: every justification is a conjunction of premise references, and different justifications are alternatives. Do not flatten this to ordinary reachability. A pair of edges `A→C, B→C` cannot distinguish “both needed” from “either sufficient.” An absence guard is an indexed dependency on a predicate/domain/interval and coverage revision; inserting an exception must invalidate it even though no positive supporting row was removed. When explanation bounds are exceeded, say explanations are incomplete while retaining whatever truth claim the solver actually established.

Keep raw signed observations outside consistency constraints. Derive `supported_positive`, `supported_negative`, `unknown`, `conflict` for an exact identity/time scope; these four evidence states are distinct from WFS's three semantic truth values. A planning policy may exclude conflicting inputs or ask for a repair, but the ledger preserves both sources. Rule provenance is not causal proof.

**2. Dependency-directed evaluation, optionally TMS/WFS.** Retain reverse indexes over fact IDs, coverage IDs, rules, negative guards and answer receipts; invalidate affected roots, lazily recompute demanded answers. Existing rooted dependencies can accelerate candidate invalidation, provided adapters supply complete dependency edges including negative dependencies. Never treat a reachability result as last-support deletion. Start with recomputation of affected strongly connected rule components. Ordinary counters work for independent extensional supports; naive recursive derivation counting can sustain an unsupported cycle.

A justification-based TMS maintains a chosen context and dependency/backtracking information. An ATMS labels conclusions with minimal consistent assumption environments and nogoods, allowing many hypothetical contexts to share work. These are explanation/context representations, not definitions of stable models or incremental database engines. ATMS is attractive for repeated “what if these components fail?” diagnosis, but minimal environments may grow exponentially. Bound it or postpone it until context reuse is a demonstrated workload.

A deterministic rule consumer can begin with stratified negation. If real negative cycles arise, WFS offers one partial interpretation with undefined atoms rather than arbitrarily choosing a stable alternative. For `a←not b; b←not a`, WFS leaves both undefined while stable semantics has two alternatives. WFS is not merely the intersection of stable models; undefined need not mean both stable possibilities exist. Do not substitute WFS for planning choices or label an unsupported external observation “false.”

**3. Retained multishot ASP workers.** Use a task/workspace-scoped clingo Control worker as an evictable cache of the committed snapshot, never the source of truth. Gate evidence/rule blocks with external activation atoms, and use solve assumptions for temporary query probes. A withdrawal deactivates its guard; it does not physically erase old grounded rules. Avoid `release_external` for reversible switches: releasing relinquishes external control. Rebase into a fresh worker when disabled history or grounded atoms reach host limits. A crashed/evicted worker rebuilds from the ledger.

The protocol must acknowledge the exact revision installed before solving, serialize changes/solves per worker, cancel by recorded worker/process identity, and preserve global admission across tenants. Keep the existing checker against the reconstructed original program, not a solver-internal transformed program. Grounded provider input makes grounding reuse a smaller benefit than in typical multishot papers; repeated search/probe setup and learned nogoods are the actual hypothesis here. Stale assumptions, permanent probe constraints and unbounded dormant history are decisive failure modes.

## Consumers and literature decisions

For dependency diagnosis, withdraw one of two independent observations and preserve readiness; withdraw the last and explain which plans require rechecking. Return possible fault sets separately from proven faults. For planning, show both viable cache/rebuild models, common consequences, and the risk observation that defeats both. A first feasible model is neither an optimum nor a unique plan; the current normal-program API supplies no optimization certificate. For claim revision, preserve a prior answer's receipt, show the new source/coverage revision that invalidated it, and distinguish changed truth from changed provenance. No automatic external action follows.

Existing [de Kleer 1986](https://doi.org/10.1016/0004-3702(86)90080-9), read pp. 127–136 on contexts, labels and nogoods, supports shared assumption environments rather than a single unexplained belief bit. Existing [van Gelder, Ross and Schlipf 1991](https://doi.org/10.1145/116825.116838), introduction and stable-model comparison, establishes the partial-model distinction. Existing [Gebser et al. 2019](https://arxiv.org/abs/1705.09811), introduction and external-atom operations, motivates controllable program blocks and separate evolving grounding/solving state; it does not supply workspace durability.

New [Hu, Motik and Horrocks 2018](https://www.cs.ox.ac.uk/people/boris.motik/pubs/hmh18optimised-maintenance.pdf), sections 1–3 and stratified semantics, explains DRed overdeletion/rederivation, B/F alternative-derivation search and why unrestricted Counting fails on recursion. These maintain a materialization, not ASP alternatives. New [Swift 2014](https://arxiv.org/abs/1405.3547), sections 1–3 on dependency graphs, lazy reevaluation and three-valued changes, supports demand-driven invalidation and view consistency rather than immediate eager recomputation everywhere. New [Özcan et al. 2025](https://proceedings.kr.org/2025/59/kr2025-0059-ozcan-et-al.pdf), introduction/background and query design, makes the limitation concrete: actual-cause queries require a supplied structural causal model and minimal contingencies. Our dependency explanations cannot inherit that claim from a graph path.

Kagi: four bounded searches, all returned results. Scry: live context/schema then three bounded catalog searches; the broad multishot query was polluted by imaging papers, so no claim of exhaustive current ASP coverage. Scry's returned corpus freshness is September 2026. Search JSON/SQL is in lane scratch. Three new PDFs/texts, hashes, URLs and reading depth are in `~/paperbin/oracle-native-20261031/revisable-reasoning/manifest.json`; foundational papers remain in the existing October 27 collection without duplication.

## Phases and rejection tests

First specify workspace mutation/revision/coverage/receipt contracts and build an authored revision scenario around the existing BuildPlan consumer. Compare every settled revision to a fresh complete solve. Required counterexamples: duplicate supports; last-support removal through a cycle; new negative exception; coverage expiry without data mutation; simultaneous withdraw/assert; contradictory sources; no stable model; odd/even negative cycles; failed solve after committed mutation; stale write; crash/replay and tenant isolation. Add shipped specialist panels only when a real specialist adapter exists; none is claimed now.

Then measure fresh full solve against dirty-root recomputation and retained multishot workers over identical histories: cold/warm p50/p95, process starts, checker cost, resident memory, grounded/dormant atoms, reset cost and output size. Include unrelated changes, duplicate supports, high fanout and a single huge affected component. Reject maintained state if its memory/coordination cost buys no meaningful end-to-end improvement. Reject explanations that confuse alternative support, assume negative coverage, or enumerate environments exponentially on the intended workload. Keep fresh solving as the reference and fallback.

Dependencies: persistence/host scout must own transaction/recovery and authority binding; provenance/source scouts must define typed source IDs, validity and coverage; planning/search scouts must distinguish feasibility, preferences and causal assumptions. Open questions are the actual long-lived revision workload, maximum demanded roots/contexts, source precedence policy, and whether WFS has a consumer beyond deterministic policy evaluation. None blocks the ledger-first design.
