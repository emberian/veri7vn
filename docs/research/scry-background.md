# Isabelle-native veri7vn: background research

Research on 2026-10-15, using [Scry](https://scry.io/) for scholarly discovery and primary-paper retrieval, followed by checks against author/project/AFP pages. This is a design input, not an agreed implementation plan. No Oracle7 implementation was changed by this research lane.

## What the literature changes about the design

The strongest precedent is an Isabelle application whose *native products* are definitions, goals, theorems, refinement relations, and reusable strategies. A query-specific answer is one product of that application; a proved general rule, improved strategy, or compiled implementation is another. Isabelle already has examples of each operation. We should compose them before inventing a separate universal language and its metatheory.

There are three different kinds of reusable improvement:

1. **Logical knowledge:** proved lemmas, definitions, refinement rules, and domain assumptions. These belong to the theory/context and can justify later results.
2. **Search knowledge:** ranking of premises, tactics, conjectures, and implementation choices. This can be heuristic or learned; its proposals must still yield accepted native results.
3. **Execution knowledge:** compiled algorithms and query plans accompanied by a theorem connecting them to their specifications. Reusing a proved algorithm avoids deriving every runtime step separately.

This distinction prevents a faster heuristic from becoming a new axiom. It also avoids treating one giant verified interpreter as the only way to obtain assurance.

## Candidate composition, for discussion

An author declares domain objects, operations, relations and assumptions as Isabelle definitions/locales and proves reusable rules. Native ML packages and Eisbach methods expose these as an application interface. An interpretation front end proposes a typed question or program with a mapping back to the original request. That interpretation is inspectable and revisable; a theorem about the proposed question does not prove that it is what the user intended.

Planning/search operates over native terms, theorem goals, contexts and explicitly tracked external data. PSL/IsaPlanner-style techniques can choose existing reasoning methods, propose missing lemmas, or request a compiler/refinement. Learned ranking can improve that search. A completed result retains its theorem and assumptions; a search trace is useful for replay and learning but is not itself a theorem.

For frequently repeated computations, the system proves a generic evaluator/query plan/algorithm correct and reuses the compiled result. Sepref provides a concrete route from mathematical containers and functional algorithms to mutable representations. This can coexist with theorem-producing conversions for symbolic transformations and small checked witnesses for selected external computations. No single mechanism must mediate every operation.

The factual database should retain source identity and rich statements. Its imported assertions are data, not axioms asserting truth in the world. Query answers can state what follows from a specified dataset and interpretation. In particular, uniqueness, negation, and absence require coverage/completeness semantics; checking one positive record cannot establish those claims. Root is investigating provenance semirings and query compilation in more detail.

## Concrete choices to settle before implementation

- Which native authoring object is primary: ordinary theory/locales plus registered tools, or a dedicated Isabelle outer-syntax command that expands into those objects? Prefer the former initially, with syntax only where repetition justifies it.
- What is the first full vertical workload? It must exercise interpretation, data access, reasoning, presentation, and reuse—not only arithmetic expression lowering.
- Which claims are conditional on imported data, and what needs complete-set evidence? This determines whether per-answer witnesses or a refined query engine is economical.
- What numerical contract is promised: mathematical exactness, rational evaluation, interval bounds, or a specified floating-point computation? They require different transformations.
- Is reuse initially theorem/rule reuse, search-trace replay, or learned/generalized strategy reuse? All are valuable; they have different acceptance tests.
- How does state enter contexts and results? Avoid hidden process-global mutable state and accidental reuse of theorems or cached answers under different assumptions.
- What is measured as performance: loading heaps, interpretation latency, proof search, reconstruction, bulk query throughput, and generated code execution should be distinguished.

## Practical status and compatibility

The current [PSL repository](https://github.com/data61/PSL) describes Isabelle2025/2025-2; an [AFP entry](https://isa-afp.org/entries/Proof_Strategy_Language.html) is available. The [Hipster repository](https://github.com/moajohansson/IsaHipster) still advertises Isabelle2019. The LLVM author page announces Isabelle2025 while retaining older prerequisite/build text. None of these statements establishes compatibility with the installed Isabelle2026-RC1. No plugin was installed, no global configuration changed, and no compatibility build was attempted by this lane.

There is sufficient prior work to avoid inventing a custom trusted kernel, a mandatory external-language representation, or a generic proof-search system from scratch. There is not enough evidence to choose and commit to every dependency before the system's native interfaces and acceptance workload are agreed.

## Scry reproduction and source discipline

The documented API contract was read at [HTTP API](https://scry.io/docs/sql-over-https) and [Errors](https://scry.io/docs/errors). `tools/research_scry.py` uses only `https://api.scry.io/v1/scry/{context,schema,query}`. It loads `~/.scry-key` within the Python process, does not put it in command arguments/output, disables redirects, verifies TLS, redacts credential occurrences in error/response text, bounds requests, and does not retry automatically. Queries carry an idempotency key derived from SQL. Default limits are 30 server seconds, 10 million nanodollars raw burden, and a maximum multiplier of 1. The raw-burden limit is not a price quotation.

```sh
.venv/bin/python tools/research_scry.py context --output var/research/scry/context.json
.venv/bin/python tools/research_scry.py schema --output var/research/scry/schema.json
.venv/bin/python tools/research_scry.py schema --relation academic.papers --output var/research/scry/schema-papers.json
.venv/bin/python tools/research_scry.py query --sql-file var/research/scry/psl.sql --output var/research/scry/psl.json
```

Read the relevant schema before writing SQL. Title search over `openalex.works.search_text_lc` is indexed and lowercase; it does not search abstracts or author names. `academic.catalog.title` is mixed-case. Exact full-text fetches use the discovered DOI-derived `paper_key` in `academic.papers`; later slashes in a DOI are encoded as `%2f`. Corpus gaps are real: some known papers were found in OpenAlex but not in the catalog/full text. Broad title queries can be dominated by unrelated biomedical or social-science literature, so useful results required narrower technical terms and primary-source checks.

Local raw query/response evidence is under `var/research/scry/` (ignored by Git). The main primary-paper collections are `fulltext.json` and `fulltext2.json`, whose rows are `[paper_key, converter, quality_label, text]`. The former has seven rows (six distinct works, since PSL has conference and preprint versions); the latter six. Search metadata is a discovery aid, not primary evidence. Extraction quality labels do not guarantee complete mathematical notation or complete documents. The PMC extraction noted above is an example.

All successful queries made by this lane to date reported `billing_mode = free_slack`, `spend_nanodollars = 0`, `deadline_partial = false`, and complete execution. A complete query does not mean complete literature coverage. These are observations for these calls, not a promise that future requests will be free. Other lanes save their own evidence in this directory; do not assume every response belongs to this lane.

No text from source papers is reproduced in this research note beyond titles and short technical names. The local retrieval files are research working material, not a redistribution package.

## Focused follow-up: valid incremental maintenance and nonmonotone provenance

[DBSP (Budiu, Chajed, McSherry, Ryzhyk, Tannen, VLDB 2023)](https://www.vldb.org/pvldb/vol16/p1601-budiu.pdf) supplies a useful semantic contract for caching under updates. With integration `I` accumulating deltas and differentiation `D` taking changes, incrementalization is `QΔ = D ∘ Q ∘ I`. Correct maintenance means the accumulated output changes equal full query evaluation at each logical transaction time. This construction alone can reconstitute the whole database; efficiency comes from replacing it with proved incremental laws for primitives and composing those laws. The [authors' formalization](https://github.com/tchajed/database-stream-processing-theory) treats finite-support integer-weighted collections, distinct, relational operators, and recursive circuits. It is a precedent to understand, not an Isabelle dependency we have adopted.

For veri7vn, the resulting design obligations are:

- A cache entry is relative to a database version, query meaning, interpretation, and assumptions. Either it is reused only at that version, or an update theorem relates its maintained state to a newer version.
- Deletions need multiplicities/support accounting: deleting one derivation may leave another. Joins need retained indexed state, and one small input update can have large output fanout.
- “Exactly one candidate” is nonmonotone. Adding a second distinct candidate invalidates a unique answer even if the original supporting record is unchanged. Maintaining the candidate map/count can handle `0 → 1 → many → 1`; caching only the winning record cannot.
- Absence and anti-joins need updates to the *excluded* relation or a versioned completeness scope. Aggregates need their stated algebra and sufficient state: count/sum can subtract contributions; deleting a minimum may require finding the next minimum. Event-time windows additionally need an explicit closure/watermark contract. These are design inferences from the maintenance invariant, not claims that DBSP automatically proves our data ingestion complete.

[Senellart's provenance-lean v1.2.0](https://zenodo.org/records/22900284) is a particularly useful semantic counterweight. Its [kind-indexed query source](https://github.com/PierreSenellart/provenance-lean/blob/v1.2.0/Provenance/AggQuery.lean) distinguishes regular, aggregate-token, and provenance columns. This is a deliberately restricted language: grouping consumes regular columns; difference/deduplication cannot operate on aggregate tokens; tokens are copied or compared through designated forms; ungrouped scalar aggregation is explicitly outside scope. We should copy the discipline of expressing scope restrictions, not assume it covers arbitrary SQL.

Its [adequacy source](https://github.com/PierreSenellart/provenance-lean/blob/v1.2.0/Provenance/QueryAdequacy.lean) proves a revealing counterexample: with two copies of `t` in `R1` and one in `R2`, provenance natural-number annotations can leave `2 ∸ 1 = 1` after deduplication and difference, while the corresponding plain set difference removes `t`. [Support adequacy](https://github.com/PierreSenellart/provenance-lean/blob/v1.2.0/Provenance/SupportAdequacy.lean) is recovered under stronger conditions, including suitable monus-preserving maps. This agrees with the broader [limitations result for difference](https://arxiv.org/abs/1105.2255): familiar equivalences do not extend uniformly to every provenance semiring. Therefore update weights, bag multiplicities, possible-world annotations, and proof provenance must not be silently conflated.
